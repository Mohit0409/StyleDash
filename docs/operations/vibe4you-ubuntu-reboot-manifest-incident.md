# Vibe4You Ubuntu Reboot Manifest Incident — 2026-10-01

## Summary

The Ubuntu production host rebooted at approximately 2026-10-01 10:13 UTC (15:43 IST).
After boot, `vibe4you-production-public.service` and `vibe4you-production-admin.service`
entered restart loops and the public site returned HTTP 502.

The reboot did not corrupt the database, fill the disk, or damage systemd configuration.
The launchers refused to start because the migration artifact integrity manifest was stale.

## Root cause

Both launchers run this integrity gate before starting Python:

`sha256sum -c --status .migration/artifact-files-remediated.sha256`

The entire manifest was checked. Exactly one entry mismatched:

`server/index.html`

PR #119, "Fix iPhone shop image uploads", merged at 2026-10-01 06:23 UTC.
The production `server/index.html` was written at 2026-10-01 07:12 UTC after that release,
but the migration-era manifest was not resealed to the validated deployed frontend.

Thus the site could continue serving the new frontend while the old process stayed alive,
but a later restart or reboot caused the launcher integrity gate to reject the valid release.

## Recovery

A candidate manifest was generated by changing only the existing `server/index.html`
hash entry to the current deployed file hash while preserving every other manifest entry.
The full candidate manifest was verified successfully before replacement.

The original manifest was preserved at:

`.migration/artifact-files-remediated.sha256.before-index-refresh-20261001T104656Z`

After the repaired manifest passed the full integrity check, systemd auto-restart recovered
the public and admin services without restoring database data or rolling back the frontend.

Post-recovery verification:

- public service: active
- admin service: active
- Cloudflare service: active
- backup timer: active
- healthcheck timer: active
- local `/api/health`: HTTP 200
- external public and health routes: HTTP 200
- external admin route: HTTP 302 through the access layer
- public `/admin`, `/styledash.db`, and `/.env`: HTTP 404
- repeated healthchecks after recovery: PASS
- failed systemd units after recovery: 0

## Required release-process correction

Any Ubuntu release that replaces a file covered by the startup integrity manifest must
atomically reseal the manifest to the exact reviewed deployed artifact before the release
is considered complete.

A deployment must not merely prove live HTTP health. It must also prove:

1. the post-deploy artifact manifest passes in full;
2. public/admin can be restarted cleanly from systemd;
3. the active release survives a controlled reboot before migration hardening is closed.

Do not weaken or remove the startup integrity gate to avoid this requirement.

## Remaining proof

The first real reboot exposed this defect and therefore does not count as a clean
reboot-recovery PASS. A second controlled reboot is still required after the manifest
repair and after the deployment procedure has been updated to keep the manifest current.
